# 팀 스터디 허브 — 설계 문서

- 작성일: 2026-08-05
- 상태: 설계 확정 (구현 계획 작성 대기)

---

## 1. 무엇을 만드는가

4인 스터디 팀이 각자 공부한 내용을 올리고, 서로 읽고, 그날 올라온 내용을 하나의 정리본으로 자동 생성하는 비공개 웹 서비스.

핵심 구조는 세 가지다.

1. **팀원별 스터디 저장소 4개** — 각자의 노트가 자기 저장소에 쌓인다.
2. **업로드** — 마크다운 본문 + 파일 첨부.
3. **날짜별 정리본** — 그날 올라온 노트를 AI가 읽고 하나의 문서로 정리한다. 웹에서 읽고 `.md` 파일로 내려받는다.

## 2. 사용자와 규모

- 사용자 4명 고정. 회원가입 없음.
- 팀 개념 없음. 데이터베이스에 팀 테이블을 두지 않는다.
- 모든 사용자가 모든 노트를 읽는다. 쓰기·수정·삭제만 본인 것으로 제한한다.

## 3. 성공 기준

- 팀원이 노트를 올리는 데 걸리는 단계가 **제목 / 날짜 / 본문**뿐이다.
- 아침에 접속하면 어제 정리본이 준비돼 있다.
- 정리본이 없는 연결고리를 지어내지 않는다.
- 운영 비용 0원.

## 4. 비목표 (이번 범위에서 제외)

의도적으로 넣지 않는 것들이다. 나중에 필요해지면 별도 설계로 다룬다.

- **첨부파일 내용 파싱·OCR** — PDF 추출, 손글씨 인식. 비용과 복잡도가 폭발하는 지점이다. 첨부는 저장·다운로드 전용.
- **개념 태그와 누적 지식맵** — 날짜를 넘나드는 연결 발견. 개념 정규화 사전이 전제인데 초기 범위를 크게 만든다. 그날 올라온 노트 사이의 연결은 정리본이 다룬다.
- 팀 여러 개, 초대 흐름, 권한 등급
- 댓글, 좋아요, 알림, 이메일 발송
- 모바일 앱 (반응형 웹으로 대응)

## 5. 기술 스택

| 영역 | 선택 | 비고 |
|---|---|---|
| 프레임워크 | Next.js (App Router) | |
| DB / 인증 / 파일 | Supabase | 무료 티어 |
| 배포 | Vercel Hobby | 크론 1일 1회 제공 |
| AI | Google AI Studio (Gemini) 무료 티어 | 호출부를 단일 모듈로 격리 |

**AI 제공자 선정 근거**: 노트가 전부 한국어이며, 무료로 열려 있는 오픈모델 대비 한국어 요약 품질이 안정적이다. 키 발급에 결제 수단이 필요 없다. 예상 사용량은 하루 1~5회로 어떤 무료 한도에도 근접하지 않는다.

**교체 가능성**: AI 호출은 `lib/ai/` 한 곳에만 존재한다. 입력은 노트 배열, 출력은 아래 §7.2의 JSON 스키마다. 다른 제공자로 바꿀 때 이 모듈만 교체한다.

## 6. 화면

| 경로 | 내용 |
|---|---|
| `/` | 오늘 날짜, 팀원 4명의 오늘 업로드 여부, 업로드 버튼, 최근 정리본 링크 |
| `/members/[slug]` | 해당 팀원의 노트 목록 (날짜 역순), 제목 검색, 월별 필터 |
| `/notes/new` | 노트 작성 |
| `/notes/[id]` | 노트 보기, 첨부 다운로드, 본인 노트면 수정·삭제 |
| `/digests` | 날짜별 정리본 목록. 각 항목에 그날 참여한 팀원 표시 |
| `/digests/[date]` | 정리본 본문, `.md` 다운로드, 다시 생성 버튼 |
| `/login` | 이메일·비밀번호 로그인 |
| `/no-access` | 로그인은 됐으나 `profiles`에 없는 계정 안내 |

**전역 내비게이션**: `홈 | 지호 민수 서연 태현 | 정리본`

팀원 4명의 이름을 상단에 고정 노출한다. 4명 고정이기에 가능한 배치이며, "저장소가 4개로 나뉜다"는 구조가 화면에 그대로 드러난다.

**홈의 업로드 현황 표시**는 기능이 아니라 장치다. 누가 아직 안 올렸는지 4명 모두에게 보이면 상호 압박이 걸린다. 스터디 서비스가 실패하는 원인은 기능 부족이 아니라 업로드 중단이다.

**업로드 폼에 태그·카테고리 입력칸을 두지 않는다.** 입력칸이 늘면 업로드율이 떨어진다.

## 7. 데이터 모델

### 7.1 테이블

```sql
profiles
  id            uuid  PK  -- auth.users.id 와 동일
  display_name  text  not null          -- '지호'
  slug          text  not null unique   -- 'jiho', URL에 사용
  avatar_url    text
  created_at    timestamptz not null default now()

notes
  id          uuid PK default gen_random_uuid()
  author_id   uuid not null references profiles(id)
  title       text not null
  body_md     text not null
  studied_on  date not null             -- 업로드 시각이 아닌 '공부한 날짜'
  created_at  timestamptz not null default now()
  updated_at  timestamptz not null default now()

attachments
  id           uuid PK default gen_random_uuid()
  note_id      uuid not null references notes(id) on delete cascade
  storage_path text not null
  file_name    text not null
  byte_size    integer not null
  mime_type    text
  created_at   timestamptz not null default now()

digests
  digest_date  date PK                  -- 하루에 정리본 하나
  body_md      text
  has_connections boolean not null default false
  status       text not null            -- 'generating' | 'done' | 'failed'
  model        text
  started_at   timestamptz              -- 생성 시작 시각 (멈춤 감지용)
  generated_at timestamptz              -- 생성 완료 시각
  error_message text
```

인덱스: `notes(author_id, studied_on desc)`, `notes(studied_on)`

**`studied_on`이 `created_at`과 분리된 이유**: 어젯밤 공부하고 다음 날 아침에 올리는 경우가 반드시 생긴다. 정리본은 `studied_on` 기준으로 묶는다. 작성자가 직접 선택하며 기본값은 오늘이다.

### 7.2 AI 응답 스키마

AI는 마크다운이 아니라 JSON을 반환한다. 마크다운 조립은 애플리케이션 코드가 한다.

```json
{
  "one_liner": "string",
  "members": [
    { "profile_slug": "jiho", "summary": "string" }
  ],
  "connections": [
    {
      "title": "string",
      "detail": "string",
      "member_slugs": ["jiho", "minsu"]
    }
  ]
}
```

`connections`는 빈 배열일 수 있다. 이것이 정상 상태다.

## 8. 정리본 파이프라인

### 8.1 실행

- **자동**: Vercel 크론이 매일 23:50 KST(= 14:50 UTC, `50 14 * * *`)에 `/api/cron/digest` 호출. `CRON_SECRET` 헤더로 인증한다.
- **수동**: `/digests/[date]` 의 "다시 생성" 버튼 → `POST /api/digests/[date]/generate`. 등록된 4명이 실행할 수 있으며 기존 정리본을 덮어쓴다.

수동 경로를 처음부터 만드는 이유는 두 가지다. 크론 이후에 올린 사람을 반영해야 하고, **Vercel 크론은 배포 후에만 동작하므로 개발 중 검증 수단이 없다.**

**대상 날짜는 KST로 명시적으로 계산한다.** 크론이 UTC로 실행되므로 서버의 기본 날짜를 그대로 쓰면 안 된다. 23:50 KST는 같은 날 14:50 UTC라서 우연히 맞아떨어지지만, 실행 시각을 15:00 UTC 이후로 옮기는 순간 조용히 전날 정리본을 생성하게 된다. 대상 날짜는 항상 `Asia/Seoul` 기준으로 구한다.

### 8.1.1 정리본 생성 API 인증 — 필수

**두 API 모두 자체적으로 인증을 수행한다. RLS에 의존하지 않는다.**

정리본 생성은 service role 키로 실행되며, **service role은 RLS를 통째로 우회한다.** 따라서 §9.2의 권한 표는 이 두 경로를 전혀 보호하지 못한다. 핸들러가 직접 막지 않으면 인터넷의 누구나 POST를 날려 Gemini 무료 한도를 소진시킬 수 있다.

| 경로 | 인증 방식 |
|---|---|
| `POST /api/cron/digest` | `CRON_SECRET` 헤더 일치 여부 검증. 불일치 시 401 |
| `POST /api/digests/[date]/generate` | 세션에서 `auth.uid()` 를 읽고, `profiles`에 해당 행이 있는지 확인. 없거나 비로그인이면 403 |

수동 경로의 검사는 `/no-access` 판정과 동일한 조건이다.

### 8.2 처리 순서

1. `studied_on = 대상 날짜` 인 노트를 전부 조회
2. 노트 0개 → 정리본을 생성하지 않고 종료 (빈 정리본으로 아카이브를 오염시키지 않음)
3. `digests` 행을 `status='generating'`, `started_at=now()` 로 upsert
4. AI 호출 → JSON 응답
5. 스키마 검증. 실패 시 1회 재시도. 두 번째도 실패하면 `status='failed'`, `error_message` 기록 후 종료
6. **연결 유효성 판정** (§8.4)
7. 마크다운 조립 → `body_md` 저장, `status='done'`, `generated_at` 기록

### 8.3 정리본 형식

```markdown
# 2026-08-05 스터디 정리

## 오늘의 한 줄
{one_liner}

## 팀원별 요약
- **지호** — {summary}
- **민수** — {summary}

## 겹치는 지점        ← 유효한 연결이 있을 때만 출력
### {title}
{detail}  (지호, 민수)
```

본문에 등장하는 팀원 이름은 해당 원본 노트로 링크한다.

`.md` 다운로드 파일명: `2026-08-05-스터디정리.md`

파일명에 한글이 들어가므로 `Content-Disposition` 헤더에 RFC 5987 형식(`filename*=UTF-8''...`)을 사용한다. 일반 `filename=` 만 쓰면 브라우저에 따라 이름이 깨진다.

### 8.4 억지 연결 방지 — 필수 요구사항

각자 자유 주제로 공부하므로, 4명이 서로 무관한 내용을 다룬 날이 자주 발생한다. 이때 AI에게 연결고리를 찾게 하면 존재하지 않는 연결을 생성한다("두 분 다 본질적으로 구조적 사고를 다루셨습니다" 류). 이런 문장이 나오기 시작하면 팀은 정리본을 신뢰하지 않게 되며, 이는 정리본이 지루한 것보다 훨씬 치명적이다.

**두 단계로 막는다.**

1. **프롬프트**: 실제로 맞닿는 지점이 없으면 `connections`를 빈 배열로 반환하라고 명시한다. 억지 연결을 금지한다고 명시한다.
2. **코드**: 프롬프트 지시에 의존하지 않는다. 각 connection 항목이 `member_slugs.length >= 2` 를 만족하고 해당 slug들이 그날 실제로 노트를 올린 사람인지 검증한다. 유효 항목이 0개면 `has_connections = false` 로 두고 **"겹치는 지점" 섹션을 마크다운에서 통째로 제거한다.**

연결이 없는 날은 아무 말도 하지 않는다. "오늘은 연결고리가 없었습니다" 같은 문장도 넣지 않는다.

### 8.5 노트가 1개인 날

요약만 출력하고 "겹치는 지점" 섹션은 나타나지 않는다 (§8.4의 검증에서 자동으로 걸러진다).

## 9. 인증과 권한

### 9.1 로그인

**이메일 + 비밀번호.** 관리자가 Supabase 대시보드에서 4개 계정을 직접 생성하고 초기 비밀번호를 팀원에게 전달한다.

```js
supabase.auth.signInWithPassword({ email, password })
```

- 가입 페이지를 만들지 않는다.
- Supabase Auth 설정에서 신규 가입을 비활성화한다.
- 비밀번호 분실 시 관리자가 대시보드에서 재설정한다. 4명 규모에서 부담이 되지 않는다.
- 세션은 자동 갱신되므로 실제 로그인 빈도는 매우 낮다.

**구글 OAuth를 선택하지 않은 이유**: 유일하게 외부 콘솔(Google Cloud Console) 작업이 필요한 방식이며, 리다이렉트 URI 설정 오류가 초기 구축에서 가장 흔한 실패 지점이다. Supabase가 두 방식을 모두 지원하므로 나중에 구글 로그인을 추가하는 것은 언제든 가능하다.

**매직링크를 선택하지 않은 이유**: Supabase 내장 메일 발송 한도가 실사용에 부족하며, 외부 메일 서비스를 붙이면 오히려 설정이 늘어난다.

**공유 비밀번호 방식을 선택하지 않은 이유**: 작성자를 식별할 수 없어 팀원별 저장소 구조가 성립하지 않는다. Supabase 인증을 쓰지 않으므로 RLS도 사용할 수 없고, 세션 처리를 직접 구현해야 해 코드가 오히려 늘어난다.

### 9.2 권한 — 2겹

**1겹: 신규 가입 차단.** Supabase Auth 설정. 편의를 위한 것이며 설정 실수로 뚫릴 수 있다.

**2겹: RLS.** 실제 방어선. 모든 정책이 "로그인한 사용자"가 아니라 **"`profiles`에 등록된 사용자"**를 요구한다.

```sql
-- 읽기: profiles에 등록된 사람만
using ( auth.uid() in (select id from profiles) )

-- 쓰기/수정/삭제: 본인 것만
using ( author_id = auth.uid() )
```

| 대상 | 읽기 | 쓰기 | 수정·삭제 |
|---|---|---|---|
| notes | 등록된 4명 | 본인 | 본인 |
| attachments | 등록된 4명 | 본인 노트 | 본인 노트 |
| digests | 등록된 4명 | 서버만 (service role) | 서버만 |
| profiles | 로그인한 사용자 (아래 주의 참조) | 없음 (대시보드에서 관리) | 없음 |

**`profiles` 테이블만 예외다.** `profiles`의 읽기 정책에 `auth.uid() in (select id from profiles)` 를 걸면 정책이 자기 자신을 조회하게 되어 **무한 재귀 오류**가 발생한다. Postgres RLS의 알려진 함정이다. 따라서 `profiles`의 읽기 정책만 다음과 같이 둔다.

```sql
-- profiles 읽기 정책
using ( auth.role() = 'authenticated' )
```

다른 테이블들이 `profiles`를 참조하는 구조는 그대로 유지된다. 등록되지 않은 계정이 `profiles`를 읽으면 팀원 4명의 이름과 slug는 보이지만, 노트·첨부·정리본은 여전히 전부 차단된다. 노출되는 정보가 이름뿐이므로 감수한다.

이 구조는 부수적으로 `/no-access` 판정에도 쓰인다. 로그인 후 `profiles`에서 `id = auth.uid()` 인 행을 조회해 없으면 미등록 계정으로 처리한다.

화면에서 버튼을 숨기는 방식에 의존하지 않는다. 주소창 직접 입력이나 클라이언트 코드 조작으로 우회할 수 없어야 한다.

크론과 정리본 생성 API는 service role 키로 서버에서만 실행한다.

### 9.3 파일 저장

- Supabase Storage **비공개 버킷**.
- 다운로드 시 짧은 만료시간(5분)의 서명 URL을 발급한다. 링크가 유출돼도 곧 무효가 된다.
- **파일당 10MB, 노트당 5개** 상한. 무료 저장소 1GB 기준으로 4명이 장기간 사용해도 여유가 있다.
- 첨부파일의 내용은 읽지 않는다 (§4 비목표).

### 9.4 비밀 관리

서버 환경변수로만 관리하며 클라이언트에 노출하지 않는다.

```
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_ANON_KEY
SUPABASE_SERVICE_ROLE_KEY      # 서버 전용
GEMINI_API_KEY                 # 서버 전용
CRON_SECRET                    # 서버 전용
```

`GEMINI_API_KEY`가 브라우저로 노출되면 제3자가 무료 한도를 소진시킬 수 있다.

## 10. 에러 처리

**원칙: 사람이 작성한 글은 어떤 경우에도 잃지 않는다.**

| 상황 | 처리 |
|---|---|
| 첨부 업로드 실패 | 본문을 먼저 저장한 뒤 첨부를 붙인다. 첨부가 실패해도 본문은 남는다. 실패한 파일만 사용자에게 알린다 |
| AI 호출 실패 | 노트는 영향 없음. `digests.status='failed'`, 정리본 페이지에 재시도 버튼 노출 |
| AI 응답 스키마 위반 | 1회 재시도. 두 번째도 실패하면 `failed` 처리. 깨진 정리본을 출력하지 않는다 |
| 권한 거부 | 빈 목록으로 두지 않고 "권한이 없습니다"를 명시적으로 표시한다 |
| 크론 미실행 | 정리본 페이지에 "아직 생성되지 않음 — 지금 생성" 버튼 표시 |
| 생성 중 프로세스가 죽음 | `status='generating'` 인데 `started_at` 이 5분 이상 지났으면 실패로 간주하고 재시도 버튼을 노출한다 |
| 로그인했으나 `profiles`에 없음 | `/no-access` 로 이동 |

권한 거부를 명시적으로 표시하는 이유: RLS가 차단하면 조회 결과가 빈 배열로 돌아와 화면상 "데이터 없음"과 구분되지 않는다. 이는 개발 중 원인 파악이 가장 어려운 실패 유형이다.

`generating` 상태에 시간 제한을 두는 이유: 함수가 타임아웃되거나 중간에 죽으면 상태가 `failed`로 바뀌지 못하고 `generating`에 영원히 머문다. 재시도 버튼은 `failed`일 때만 뜨므로, 사용자는 끝나지 않는 로딩 표시를 보며 아무것도 할 수 없게 된다. `started_at` 경과 시간으로 이 상태를 빠져나온다.

## 11. 테스트

4명 규모에 전면적인 E2E는 과잉이다. 다음 셋만 작성한다.

1. **권한 테스트 (최우선)**
   - 타인의 노트 수정·삭제 시도 → 거부
   - `profiles`에 없는 계정의 노트 조회 → 빈 결과
   - 비로그인 상태의 API 접근 → 거부
   - **미등록·비로그인 계정의 `POST /api/digests/[date]/generate` 호출 → 403** (§8.1.1)
   - `CRON_SECRET` 없이 `POST /api/cron/digest` 호출 → 401

   권한 결함은 조용히 존재하며 사용 중에 드러나지 않는다.

2. **정리본 생성 로직** — AI 응답을 목(mock)으로 주입하고 네 경우를 검증한다.
   - 노트 0개 → 정리본 생성 안 함
   - 노트 1개 → 요약만, "겹치는 지점" 없음
   - `connections: []` → **"겹치는 지점" 섹션이 마크다운에 존재하지 않음**
   - 유효한 연결 있음 → 정상 출력

   세 번째 케이스가 §8.4 요구사항의 검증 지점이다.

3. **마크다운 다운로드** — 파일명 형식과 본문 내용 일치

**실제 AI를 호출하는 테스트는 작성하지 않는다.** 무료 한도를 소모하고, 응답이 비결정적이라 테스트가 무작위로 실패한다. 응답은 목으로 대체하고 애플리케이션 코드만 검증한다.

## 12. 제약과 리스크

| 항목 | 내용 | 대응 |
|---|---|---|
| 무료 Gemini API 데이터 취급 | 전송된 노트 본문이 모델 개선에 사용될 수 있다 | 팀에 사전 공유. 기밀 정보를 올리지 않는다 |
| Supabase 무료 프로젝트 일시정지 | 약 7일 이상 미사용 시 자동 정지 | 매일 사용하므로 실질적 영향 없음. 정지돼도 접속 시 복구되며 첫 접속만 느리다 |
| Vercel Hobby 크론 | 1일 1회만 가능 | 요구사항이 1일 1회이므로 부합. 더 잦은 실행이 필요한 기능을 설계하지 않는다 |
| 정리본 품질 | AI 요약이 기대에 못 미칠 수 있다 | 원본 노트가 항상 보존되며 링크된다. 정리본은 보조 수단이다 |
| Storage 1GB | 첨부 누적 | 파일당 10MB 상한. 초과 시 오래된 첨부 정리 |

## 13. 구현 단계

한 번에 전체를 구현하지 않는다. 단계마다 배포 가능한 상태를 만든다.

**1단계 — 사용 가능한 최소 형태**
로그인, `profiles`, 노트 CRUD, 팀원별 저장소 4개, 홈 화면, RLS 정책 및 권한 테스트.
→ 이 시점에서 팀이 실사용을 시작할 수 있다. 정리본이 없어도 "각자 올리고 서로 읽는다"는 절반이 동작한다.

**2단계 — 첨부파일**
Storage 버킷, 업로드, 서명 URL 다운로드, 용량 상한.

**3단계 — 정리본**
AI 모듈, 응답 스키마 검증, 연결 유효성 판정, 마크다운 조립, 수동 생성 API, 크론 등록, `.md` 다운로드, 아카이브 화면.

수동 생성 API를 크론보다 먼저 만든다. 크론은 배포 후에만 검증할 수 있기 때문이다.

## 14. 사람이 직접 해야 하는 설정

코드로 자동화할 수 없는 작업들이다. 처음 수행하면 합쳐서 1~2시간이 소요된다.

1. Supabase 프로젝트 생성
2. Supabase Auth에서 신규 가입 비활성화
3. 팀원 4명 계정 생성 (Authentication → Users → Add user). 생성된 각 사용자의 **`auth.users.id`(uuid)를 복사해 `profiles.id` 에 그대로 넣는다.** 두 값이 같아야 권한 정책이 동작한다. 함께 `display_name`(예: 지호)과 `slug`(예: jiho)를 입력한다
4. Google AI Studio에서 Gemini API 키 발급
5. Vercel 프로젝트 연결 및 환경변수 5개 입력
6. Storage 비공개 버킷 생성

## 15. 알려진 함정

구현 중 시간을 소모할 가능성이 높은 지점을 미리 기록한다.

- **RLS 차단은 에러가 아니라 빈 결과로 나타난다.** 노트를 분명히 저장했는데 목록이 비어 보이면 대부분 권한 문제다. §10의 명시적 표시가 이를 완화한다.
- **RLS 정책이 자기 테이블을 조회하면 무한 재귀 오류가 난다.** `profiles`가 여기 해당한다. §9.2의 예외 처리를 반드시 적용한다.
- **Vercel 크론은 UTC 기준이다.** 23:50 KST는 `50 14 * * *` 이다.
- **Vercel 크론은 배포 환경에서만 동작한다.** 로컬에서는 수동 생성 API로 검증한다.
