## S1. 밤에 공부하고 다음 날 아침에 올린다 ★

> 지호가 화요일 밤 11시에 공부를 마쳤다. 피곤해서 그냥 잤다. 수요일 아침 출근길에 올린다.

1. `/` 접속 → 이미 로그인 상태 (세션 자동 갱신)
2. "오늘 내 스터디 올리기" 클릭
3. **날짜 칸을 어제로 바꾼다.** 기본값은 오늘이다
4. 제목·본문 입력 → 저장 → `/notes/{id}` 로 이동

**→ 설계 근거:** 이 시나리오 때문에 `studied_on`(공부한 날)과 `created_at`(올린 시각)이 별도 컬럼이다. 정리본은 `studied_on` 기준으로 묶는다. 그렇지 않으면 어젯밤 공부한 내용이 오늘 정리본에 섞여 들어간다.

이런 경우는 예외가 아니라 **반드시 생긴다.**

## S2. 클로드가 정리해준 `.md`를 올린다

> 민수는 공부하면서 클로드와 대화하고, 마지막에 "정리해서 md로 줘"라고 한다. 그 파일을 올린다.

1. `/notes/new` → 폼 맨 위 **"마크다운 파일 불러오기"** 에서 파일 선택
2. 브라우저가 `file.text()` 로 읽는다. `.md` 가 아니면 거절한다
3. 맨 앞 빈 줄을 건너뛴 첫 줄이 `# 제목` 이면 그걸 제목 칸에, 나머지를 본문 칸에 넣는다. `#` 이 없으면 **확장자를 뗀 파일명**이 제목이 되고 본문은 원본 그대로
4. **불러온 뒤에도 수정 가능.** 직접 타이핑하는 길도 그대로 남아 있다
5. 저장 → 본문은 `react-markdown` 으로 렌더링돼 보인다

파일은 서버로도 스토리지로도 가지 않는다. 브라우저가 읽어서 텍스트로 만들고, 그 텍스트가 평소처럼 저장된다.

**→ 설계 근거:** 이 시나리오가 확인되면서 2단계 범위가 통째로 바뀌었다. "파일을 보관했다가 나중에 내려받는다"에서 "파일을 읽어서 본문 칸을 채운다"로. 스토리지 버킷·업로드 컴포넌트·서명 URL 다운로드·스토리지 권한 정책이 전부 불필요해졌다.

`.md` 는 그냥 텍스트라 PDF·손글씨와 달리 파싱이 필요 없다. 본문이 DB에 텍스트로 들어가므로 3단계 AI 정리본도 그대로 살아 있다. 자세한 경위는 [2단계 계획서](2026-08-05-study-hub-phase2-plan.md) 상단의 경고 블록에 있다.

## S3. 남의 저장소를 읽는다

> 서연이 "태현이가 요즘 뭐 공부하지?" 하고 궁금해한다.

1. 내비에서 **태현** 클릭 → `/members/taehyun`
2. 노트 목록이 날짜 역순으로 뜬다. 총 개수도 함께
3. 제목으로 검색하거나 월별로 필터링
4. 노트를 열어 읽는다 — **수정·삭제 버튼은 보이지 않는다**

**→ 설계 근거:** 버튼이 안 보이는 건 편의일 뿐이다. 주소창에 `/notes/{id}/edit` 을 직접 쳐도 소용없다. **Postgres RLS가 막는다.** 화면에서 버튼을 숨기는 방식에 의존하지 않는다.

## S4. 등록되지 않은 계정으로 로그인한다

> 누군가 Supabase에 계정은 만들어졌는데 `profiles` 에 행을 안 넣었다. 또는 UID를 잘못 복사했다.

1. `/login` 에서 로그인 성공
2. `requireProfile()` 이 `profiles` 에서 해당 행을 못 찾는다
3. `/no-access` 로 이동 — "등록되지 않은 계정입니다"

**→ 설계 근거:** 이 화면이 없으면 어떻게 되나. RLS가 차단할 때 에러가 아니라 *빈 배열*이 돌아온다. 그러면 화면상 "아직 아무도 안 올렸습니다"와 구분되지 않는다. 로그인은 되는데 모든 목록이 텅 빈 상태를 보게 되고, 원인을 찾는 데 몇 시간이 걸린다.

그래서 **접근 거부는 빈 목록이 아니라 명시적인 화면으로 표시한다.** 이것이 개발 중 원인 파악이 가장 어려운 실패 유형이다.

## S5. 아침에 어제 정리본을 확인한다

> 목요일 아침. 어제 뭐가 올라왔는지 한 번에 보고 싶다.

1. 홈 상단의 **"최근 정리본 (2026-08-05) →"** 링크를 바로 누르거나, 내비 **정리본** → `/digests` 목록으로 간다
2. 목록에는 **완료된 정리본만** 뜬다. 각 줄에 그날 참여한 팀원 이름이 붙는다
3. 날짜 클릭 → `/digests/2026-08-05`
   - **오늘의 한 줄**
   - **팀원별 요약** — 이름이 그 사람의 저장소(`/members/{slug}`)로 링크된다
   - **겹치는 지점** — *유효한 연결이 있는 날에만 나타난다*
4. 필요하면 **`.md` 다운로드** (`2026-08-05-스터디정리.md`)

전날 밤 23:50 KST에 크론이 이미 만들어놨다. 크론 이후에 누가 올렸다면 **다시 생성** 버튼으로 갱신한다.

**→ 설계 근거:** 다운로드 파일명에 한글이 들어가므로 `Content-Disposition` 에 RFC 5987 형식(`filename*=UTF-8''...`)을 쓴다. 일반 `filename=` 만 쓰면 브라우저에 따라 이름이 깨진다.

목록에서 `status='done'` 만 거르는 것도 같은 결의 판단이다. 생성 중이거나 실패한 날짜가 목록에 섞이면 클릭했을 때 빈 화면을 보게 된다.

## S6. 크론이 실행되지 않았다

> 금요일 아침에 들어갔는데 정리본이 없다.

`/digests/2026-08-07` 로 직접 들어가면 상태에 따라 세 화면 중 하나가 나온다.

| `digests` 행 상태 | 화면 |
|---|---|
| 행 자체가 없음 | "아직 생성되지 않았습니다." + **생성 버튼** |
| `failed` | "생성에 실패했습니다." + **생성 버튼** |
| `generating` | "생성 중입니다." + **생성 버튼** |

어느 경우든 버튼이 있다. 버튼은 `POST /api/digests/{date}/generate` 를 부르고, 성공하면 화면을 새로 고친다.

**→ 설계 근거:** `generating` 에도 버튼을 띄우는 게 핵심이다. 함수가 타임아웃되거나 중간에 죽으면 상태가 `failed` 로 바뀌지 못하고 `generating` 에 영원히 머문다. 버튼을 `failed` 일 때만 띄웠다면 사용자는 **끝나지 않는 로딩 표시를 보며 아무것도 할 수 없게 된다.**

> 설계 문서 §10은 이 문제를 "`started_at` 이 5분 이상 지났으면 실패로 간주"로 풀려고 했다. 구현은 더 단순하게 갔다 — **상태와 무관하게 항상 버튼을 노출한다.** 경과 시간을 재지 않으므로 `started_at` 은 기록만 되고 판정에 쓰이지 않는다. 같은 문제를 조건 없이 막는 쪽이 빠져나갈 구멍이 적다.

수동 생성 API를 크론보다 **먼저** 만든 이유도 여기 있다. Vercel 크론은 배포 후에만 동작해서 개발 중 검증 수단이 없다.

## S7. 아무도 안 올린 날

정리본을 **아예 만들지 않는다.** `runDigestPipeline` 이 노트 0개를 확인하면 `digests` 행을 건드리지도 않고 `skipped: true` 로 끝난다. 빈 정리본으로 아카이브를 오염시키지 않는다. 같은 이유로 마인드맵 분류도 만들지 않는다 — `knowledge_generations` 행 자체가 생기지 않는다.

노트가 1개뿐인 날은 요약만 나오고, "겹치는 지점" 섹션은 자동으로 사라진다 — `filterValidConnections` 가 `member_slugs.length >= 2` 를 요구하므로 혼자인 날은 어떤 연결도 통과하지 못한다.

**→ 설계 근거:** "오늘은 연결고리가 없었습니다" 같은 문장도 넣지 않는다. 연결이 없는 날은 아무 말도 하지 않는다.

`assembleDigestMarkdown` 은 `connections` 가 비면 그 섹션의 제목 줄조차 만들지 않는다. AI에게 마크다운을 통째로 받았다면 불가능했을 처리다.

## S8. 마인드맵에서 왜 이렇게 분류됐는지 확인한다 ★ 신규

> 태현이 `/mindmap`에서 "이분 탐색"이라는 주제 노드를 눌렀다. 자기가 올린 적 없는 노트 점이 하나 걸려 있다. "내가 언제 이걸 올렸지?" 싶어 확인해본다.

1. `/mindmap` → 주제 노드 "이분 탐색" 클릭 → 그 아래 노트 점들이 펼쳐진다
2. 낯선 점에 마우스를 올린다 → 툴팁에 **AI가 분류 근거로 쓴 원문 발췌**가 그대로 뜬다 (예: "…정렬된 배열에서 절반씩 줄여나가는 방식으로…")
3. 발췌를 읽고 "아, 내가 그래프 탐색 노트에 곁다리로 이분 탐색 얘기를 적었었지" 하고 납득한다
4. 점을 클릭 → 원본 노트(`/notes/{id}`)로 이동해 전체 맥락을 확인한다

만약 AI가 근거 없이 억지로 분류했다면, 애초에 이 매핑은 DB에 저장조차 되지 않는다 — 서버가 `evidence_quote`를 노트 원문에서 실제로 찾을 수 있는지 먼저 확인하고, 못 찾으면 그 노트-주제 연결 자체를 버리기 때문이다.

**→ 설계 근거:** 4단계는 §5(성공 기준)의 "정리본이 없는 연결고리를 지어내지 않는다"를 마인드맵까지 그대로 확장한 결과다. 정리본이 "이 연결의 양쪽 다 그날 실제로 노트를 올렸는가"를 코드로 검증하듯, 마인드맵은 "이 분류의 근거 문장이 그 노트에 실제로 있는가"를 코드로 검증한다. 사람이 승인/반려하는 검수 UI를 따로 만드는 대신, **분류 자체를 원문과 대조해 결정론적으로 걸러내는 쪽**을 택했다 — 4명 규모에서 검수 큐를 만드는 건 관리 부담만 늘린다.

## 시나리오가 만든 설계 결정 요약

| 시나리오 | 만들어낸 결정 |
|---|---|
| S1 | `studied_on` 을 `created_at` 과 분리 · 날짜 직접 선택 |
| S2 | 2단계 범위 전면 재조정 (스토리지 → 브라우저 파일 읽기) |
| S3 | 권한을 화면이 아닌 RLS로 강제 |
| S4 | `/no-access` 명시 화면 · 접근 거부를 빈 목록으로 두지 않음 |
| S5 | 정리본 아카이브 · `done` 만 목록에 노출 · RFC 5987 파일명 |
| S6 | 상태와 무관하게 생성 버튼 상시 노출 · 수동 생성 API를 크론보다 먼저 |
| S7 | 노트 0개면 생성 안 함 · 연결 없으면 섹션 제거 · 마인드맵도 동일 |
| S8 | 근거 문장 원문 대조 검증 · 사람 검수 UI 대신 결정론적 필터링 |
